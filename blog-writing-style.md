# Auth0 Blog Writing Style Guide

This guide captures the authentic writing patterns from successful Auth0 blog posts. Use it to create content that sounds human, expert, and engaging.

## Core Principles

1. **Be direct, be helpful, be human** - Get to the point. Respect the reader's time.
2. **Expertise without arrogance** - You know your stuff, but you're teaching, not showing off.
3. **Practical over theoretical** - Every concept ties back to real-world application.
4. **Show, don't just tell** - Code examples, scenarios, and concrete cases beat abstract explanations.

## Voice & Tone by Pillar

Use the following voice and tone guidelines based on the type of content you are going to create.

### Expert POV

- First-person, conversational
- Take clear stances: "I believe..." or "In my experience..."
- Share failures alongside successes
- Use "we" when describing team decisions

### Proprietary Data & Research

- Precise and analytical
- Let the data speak: "The numbers show..." not "We think..."
- Explain methodology upfront
- Be confident in findings, humble about interpretations

### Product How-To

- Instructional but friendly
- Use "you" and "your" liberally
- Guide with "Let's..." to walk alongside the reader
- Anticipate confusion: "You might wonder why..."

### Rapid-Response

- Urgent but calm
- Lead with what readers need to do
- Be clear about severity and scope
- Skip the background, link to it instead

### Authentic Voices

- Warm and personal
- Celebrate specific achievements
- Include the messy parts of the journey
- Let the subject's personality shine through

### Marketing

- Confident and forward-looking
- Focus on customer benefits, not feature lists
- Use concrete examples of impact
- Balance excitement with substance

## Sentence Structure

### DO:

- **Start with the point.** Don't bury the lead.
- **Use active voice.** "The function returns a token" not "A token is returned by the function."
- **Keep sentences short for complex topics.** One idea per sentence when explaining hard concepts.
- **Address the reader directly.** "You'll need to configure..." not "Users need to configure..."
- **Use contractions.** "You'll", "don't", "isn't" sound more natural than their formal versions.

### DON'T:

- Don't start too many sentences with "This" or "It" without clear antecedents.
- Don't write sentences longer than 25 words when explaining technical concepts.
- Don't use passive voice unless the actor is truly irrelevant.

## Words & Phrases to AVOID (AI Tells)

These patterns make content sound AI-generated. Eliminate them completely.

### Em Dashes

**Never use em dashes (—) for parenthetical asides.**

| Instead of                                                        | Write                                                           |
| ----------------------------------------------------------------- | --------------------------------------------------------------- |
| "The token — which contains user claims — expires after 24 hours" | "The token (which contains user claims) expires after 24 hours" |
| "MFA — when implemented correctly — blocks most attacks"          | "MFA blocks most attacks when implemented correctly."           |
| "OAuth 2.0 — the industry standard — provides..."                 | "OAuth 2.0, the industry standard, provides..."                 |

### Filler Phrases

These add nothing. Delete them.

| Remove                               | Replace with                        |
| ------------------------------------ | ----------------------------------- |
| "It's worth noting that..."          | (just state the fact)               |
| "In order to..."                     | "To..."                             |
| "It's important to remember that..." | (just state it)                     |
| "At the end of the day..."           | (delete entirely)                   |
| "When it comes to..."                | (start with the topic)              |
| "In terms of..."                     | (delete or rephrase)                |
| "The fact that..."                   | (delete, state directly)            |
| "It goes without saying..."          | (then don't say it, or just say it) |
| "Needless to say..."                 | (same as above)                     |
| "As you may know..."                 | (just state it)                     |

### Overused AI Words

These words scream "AI wrote this." Find alternatives.

| Avoid           | Use instead                              |
| --------------- | ---------------------------------------- |
| "delve"         | explore, examine, look at, dig into      |
| "dive deep"     | examine closely, look at in detail       |
| "journey"       | process, experience, path                |
| "landscape"     | market, space, field, industry           |
| "leverage"      | use                                      |
| "utilize"       | use                                      |
| "robust"        | strong, reliable, solid                  |
| "seamless"      | smooth, easy                             |
| "streamline"    | simplify, speed up                       |
| "empower"       | enable, help, let                        |
| "unlock"        | enable, reveal, access                   |
| "harness"       | use, apply                               |
| "revolutionize" | change, improve, transform               |
| "cutting-edge"  | modern, latest, new                      |
| "game-changer"  | important improvement, significant shift |
| "best-in-class" | leading, top                             |
| "holistic"      | complete, comprehensive, full            |

### Weak Constructions

| Avoid                         | Write instead            |
| ----------------------------- | ------------------------ |
| "There are many ways to..."   | "You can..."             |
| "One thing to consider is..." | (just state the thing)   |
| "The reason why X is that Y"  | "X because Y"            |
| "In this article, we will..." | (just start the content) |

## Title Patterns by Pillar

Use the following patternd for titles based on the type of content you are going to create.

### Expert POV

Strong patterns:

- "Why I [Did X] After [Y Years/Experience]"
- "The [Mistake/Lesson] That [Taught Me/Cost Us] [Specific Outcome]"
- "[Number] Things I Wish I'd Known About [Topic]"
- "What [Specific Experience] Taught Me About [Topic]"

Weak (avoid):

- "My Thoughts on [Topic]"
- "Some Advice About [Topic]"

### Proprietary Data & Research

Strong patterns:

- "We Analyzed [X Data Points]: Here's What We Found"
- "[Data-Driven Finding]: Data from [Sample Size]"
- "State of [Topic] [Year]: Insights from [Data Source]"

Weak (avoid):

- "Research About [Topic]"
- "What the Data Says About [Topic]"

### Product How-To

Strong patterns:

- "Implementing [Feature] in [Framework]: A Practical Guide"
- "[Task]: From Zero to Production"
- "Building [Specific Thing] with [Technology]"
- "[Problem]? Here's How to Fix It"

Weak (avoid):

- "How to [Basic Task]" (too generic)
- "The Complete Guide to [Topic]" (unless truly complete)
- "Everything You Need to Know About [Topic]"

### Rapid-Response

Strong patterns:

- "[CVE/Issue]: What You Need to Do Now"
- "[News Event]: How This Affects Your [Stack/Team]"
- "[Vulnerability] Explained: Action Required"

Weak (avoid):

- "Breaking News: [Topic]"
- "Important Update About [Topic]"

### Authentic Voices

Strong patterns:

- "How [Company] [Achieved Specific Result] with [Approach]"
- "From [Starting Point] to [End Point]: [Person/Team]'s Story"
- "[Role] at [Company]: What I've Learned About [Topic]"

### Marketing

Strong patterns:

- "Introducing [Feature]: [Primary Benefit]"
- "[Feature Name]: [What It Does] for [Who]"
- "Now Available: [Feature] for [Use Case]"

Weak (avoid):

- "Announcing Our New [Feature]!" (too generic)
- "[Feature] Is Here!" (no context)

### Thought Leadership

Strong patterns:

- "What [Emerging Trend] Means for [Audience/Industry]"
- "Why [Trend] Will Define [Year/Context]"
- "How [Shift] Is Changing [Domain]"
- "Where [Technology/Practice] Is Headed Next"

Weak (avoid):

- "Thoughts on [Topic]"
- "[Topic]: A Deep Dive" (AI-sounding colon format)
- "[Trend]: What It Means for [Industry]" (colon format)
- "The State of [Topic]" (too generic without data)

## Code Examples

### Format Guidelines

- Always show complete, runnable snippets (not fragments)
- Include necessary imports and setup
- Add comments for non-obvious lines only
- Use realistic variable names (not `foo`, `bar`, `myVariable`)

### Context Guidelines

- Explain WHAT the code does before showing it
- Show the WHY, not just the HOW
- Include expected output when helpful
- Highlight the important lines after the snippet

### Before/After Pattern

When showing improvements, use this structure:

```
The traditional approach looks like this:

[code block - before]

This works, but [explain limitation]. Here's a better approach:

[code block - after]

Notice how [point out the key improvement].
```

### Error Handling

When showing code that could fail:

- Include realistic error handling
- Show what errors to expect
- Explain recovery strategies

## Pillar Mastery

This section provides concrete patterns for writing in each pillar's voice. Use these examples, opening patterns, rhythm guidance, and transitions to produce precise, authentic content.

### Example Excerpts by Pillar

**Expert POV** — First-person, opinionated, based on real experience:

> I've implemented OAuth flows at three different companies, and I made the same mistake every time: treating refresh tokens as an afterthought. At my last startup, this cost us a week of emergency patches and one very angry enterprise customer.
>
> Here's what nobody tells you about refresh token rotation: the spec makes it sound simple, but production is full of edge cases. What happens when the rotation request fails mid-flight? What about mobile apps that go offline for days?
>
> The approach I recommend now is defensive by default. Assume the rotation will fail. Build retry logic before you need it.

**Proprietary Data & Research** — Precise, data-driven, methodology-first:

> We analyzed 2.3 million authentication events across 847 Auth0 tenants to understand how MFA adoption affects account takeover rates. The results were clearer than expected.
>
> Tenants with MFA enabled on 90%+ of accounts saw a 94% reduction in successful credential-stuffing attacks. But the more interesting finding was in the middle tier: partial MFA adoption (30-60% of accounts) showed only a 23% reduction. Half-measures don't work.
>
> Our methodology focused on comparing attack patterns before and after MFA rollouts, controlling for traffic volume and industry vertical.

**Product How-To** — Instructional, friendly, walking alongside the reader:

> Let's add passwordless authentication to your React app. You'll need an Auth0 account and about 15 minutes.
>
> First, grab your Auth0 domain and client ID from the dashboard. You'll find these under Applications → Settings. Keep this tab open; we'll need these values in a moment.
>
> You might wonder why we're using the SPA SDK instead of a redirect flow. For this use case, the embedded approach gives us more control over the user experience without sacrificing security.

**Rapid-Response** — Urgent, clear, action-first:

> Action required: A critical vulnerability (CVE-2026-1234) affects jwt-decode versions 3.x. If you're using this library, upgrade to 4.0.1 immediately.
>
> Check your package.json now. Run `npm ls jwt-decode` to see your installed version.
>
> This vulnerability allows attackers to forge token signatures under specific conditions. Exploitation in the wild has been confirmed.

**Authentic Voices** — Warm, narrative, personality-forward:

> When Sarah Chen joined Acme Corp as their first security engineer, the authentication system was held together with duct tape and good intentions. "We had passwords stored in a spreadsheet," she laughs. "Not even a protected spreadsheet."
>
> Three years later, Acme processes 50 million authentications daily with 99.99% uptime. The journey from spreadsheet to scale wasn't linear, and Sarah is refreshingly honest about the missteps along the way.
>
> "I tried to implement SSO before we had basic logging in place. Classic mistake. You can't secure what you can't see."

**Marketing** — Confident, benefit-focused, forward-looking:

> Actions for Auth0 is now generally available. Define custom logic that runs during authentication—without managing infrastructure.
>
> Teams at Snyk, Delivery Hero, and Notion have already deployed Actions to enforce custom MFA policies, enrich tokens with business data, and block suspicious logins in real time.
>
> Start with our pre-built templates or write your own. Actions run on Auth0's edge network, so latency stays under 100ms even for complex flows.

**Thought Leadership** — Conceptual, analytical, forward-facing:

> The identity landscape is shifting faster than most security teams realize. Passkeys went from experiment to expectation in under 18 months. Device trust is becoming table stakes. And the boundary between authentication and authorization keeps getting blurrier.
>
> What we're seeing isn't just technology evolution—it's a fundamental rethink of what "identity" means in distributed systems. The companies adapting quickly share one trait: they stopped treating identity as an infrastructure problem and started treating it as a product.
>
> This shift has implications for how we build teams, evaluate vendors, and measure success. The metrics that mattered five years ago—uptime, latency—are now assumed. The new questions are about adaptability and user experience.

## Section Structure

### Opening Paragraph

- Lead with the problem or question
- State what the reader will learn
- Keep it under 3 sentences
- NO "In this article, we will..."

Good example:

> JWT refresh tokens are supposed to improve security. But I've seen them implemented in ways that actually make things worse. Here's how to avoid the most common mistakes.

Bad example:

> In this comprehensive article, we will delve into the world of JWT refresh tokens and explore the various ways they can be implemented in your application.

### Body Sections

- Each H2 should describe what the section DOES for the reader
- Good: "Setting Up the Auth Middleware"
- Bad: "Auth Middleware" or "About Auth Middleware"
- Use H3 for sub-steps or variations
- End significant sections with a brief summary or transition

### Code Sections

1. Brief intro (1-2 sentences max)
2. Code block
3. Explanation of key parts
4. Common variations or gotchas

### TL;DR Sections (for long articles)

Place after the opening paragraph for posts over 1500 words:

- 3-5 bullet points maximum
- Actionable takeaways, not summaries
- Link to relevant sections

### Conclusion

- Summarize key actions, not concepts
- Point to next steps or related resources
- End with the practical "so what"
- NO "In conclusion..." or "To sum up..."

## Common Gotchas

### Anthropomorphizing Code

| Avoid                       | Use instead                        |
| --------------------------- | ---------------------------------- |
| "The function wants to..."  | "The function expects..."          |
| "JavaScript thinks that..." | "JavaScript interprets this as..." |
| "The API is trying to..."   | "The API attempts to..."           |

### Hedging Too Much

| Avoid                            | Use instead                     |
| -------------------------------- | ------------------------------- |
| "This might possibly help..."    | "This helps..."                 |
| "You could potentially use..."   | "Use..." or "Consider using..." |
| "It seems like this could be..." | "This is..."                    |

### Over-Qualifying

| Avoid                                  | Use instead                    |
| -------------------------------------- | ------------------------------ |
| "In most cases, generally speaking..." | "Usually..." or "Typically..." |
| "There are some situations where..."   | "Sometimes..."                 |

## Voice Authenticity Checks

Use these checks to ensure content doesn't sound AI-generated:

### Opening Authenticity

- Opening contains specific scenario/experience, not generic framing
- Uses "I/we" perspective where pillar calls for it (Expert POV, Authentic Voices, Thought Leadership)
- Includes at least one concrete detail (number, quote, name, or specific outcome)

### Sentence Variety

- Mix of sentence lengths (average <20 words per sentence)
- At least one single-sentence paragraph for emphasis
- Varied sentence starters (don't begin 3+ paragraphs with "The")

### Word Choices

- Specific verbs instead of vague ones ("replaces" not "affects", "breaks" not "impacts")
- Reader-facing language ("you'll find", "you might wonder") present
- At least 3 contractions per 1000 words

### Opinion & Stance

- For opinion pillars: At least 2 clear positions with reasoning
- No excessive hedging ("might", "could", "seems") in action sections
- Conclusion offers perspective, not just summary

### AI-Sounding Red Flags

Rewrite these patterns when found:

| Red Flag                            | Better Approach                           |
| ----------------------------------- | ----------------------------------------- |
| "One thing to consider"             | State the specific consideration directly |
| "Various approaches exist"          | Name 2 approaches and compare them        |
| "It depends on your needs"          | Specify when and why it depends           |
| "There are several ways to"         | Pick the best way and explain why         |
| "It's important to understand"      | Just explain it directly                  |
| "Let's explore" without destination | State what you'll cover specifically      |
| "In today's landscape"              | Name the specific context                 |
| "As we all know"                    | Either explain it or don't mention it     |
